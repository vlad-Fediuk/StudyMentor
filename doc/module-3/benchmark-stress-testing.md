## 1. Мета роботи та конфігурація тестового середовища

**Мета тестування:**
1. Визначити базові показники продуктивності (**Benchmark Testing**) REST API `StudyMentor` за допомогою консольної утиліти **Apache Benchmark (`ab`)** за різних рівнів одночасних запитів ($c = 5, 20, 50, 100$).
2. Провести стрес-тестування (**Stress Testing**) та пікове тестування (**Spike Testing**) за допомогою **Grafana k6** для визначення межі стабільної роботи системи, динаміки деградації часу відповіді ($p_{95}$) та поведінки сервера за навантаження до 300 віртуальних користувачів (VU).
3. Сформувати гіпотези щодо вузьких місць архітектури для подальшої верифікації під час профілювання (`Profiling`) та оптимізації запитів до бази даних (`Database Optimization`).

### Параметри середовища та умови вимірювання:
- **Сервер застосунку:** ASP.NET Core 10.0 Minimal API (`Kestrel`), запущений у конфігурації **Release** (`dotnet run -c Release --project study-mentor-api --launch-profile http`, адреса `http://localhost:5132`).
- **Конфігурація ізоляції:** `RateLimiting__Enabled=false`, `Caching__Enabled=false` (базові виміри знято до ввімкнення кешування та рефакторингу).
- **СУБД:** PostgreSQL 16 (`pgvector/pgvector:pg16` у Docker-контейнері `study-mentor-db`, порт `55432`).
- **Обсяг тестових даних ([`seed.sql`](benchmark/seed.sql)):**
  - `majors`: **20** записів;
  - `subjects`: **200** записів;
  - `lectures`: **5 000** записів;
  - `users`: **50 000** записів (`50` груп);
  - `exercises` (`Flashcard`): **200** наборів;
  - `exercises` (`Test`): **2 000** тестів, **6 000** питань (`test_questions`), **24 000** варіантів відповідей (`test_answer_variants`).
- **Тестовані endpoint-и (без побічних ефектів модифікації даних):**
  1. `GET /lectures` — основний endpoint: повертає список із 5 000 лекцій разом із вкладеними об'єктами `SubjectResponse` та `MajorResponse` (розмір JSON-відповіді — **1 748 317 байтів ≈ 1.75 МБ**).
  2. `GET /tests?sourceFlashcardId=58cbc2f9-f0ab-024e-2005-4cb619d7d242` — додатковий endpoint: повертає тести, згенеровані на основі конкретного набору карток (10 тестів із 2 000, розмір JSON-відповіді — **23 909 байтів**).
- **Інструменти:**
  - **Apache Benchmark (`ab`)** v2.3 (Revision 1934973, Apache Lounge Win64) — по 3 прогони після прогріву (warm-up) для кожного рівня паралельності, у звіт взято **медіанний прогін**.
  - **Grafana k6** v0.54.0 (`windows/amd64`) — сценарії [`stress-test.js`](benchmark/stress-test.js) та [`spike-test.js`](benchmark/spike-test.js).
  - **Моніторинг ресурсів:** оскільки ні `ab`, ні `k6` штатно не збирають метрики процесора й пам'яті серверного процесу ОС, показники CPU (%) та RAM (`WorkingSet64`, МБ) процесу `study-mentor-api` паралельно фіксувалися через системний моніторинг (`Get-Process` та `dotnet-counters`).

## 2. Етап 1. Базове вимірювання продуктивності (Benchmark Testing — Apache Benchmark)

### 2.1. Тестування основного endpoint-а `GET /lectures` ($n = 1000$)

Виконано серії по $n = 1000$ запитів при рівнях паралельності $c = 5, 20, 50, 100$ (по 3 прогони на кожному рівні).

#### Рівень 1: $c = 5$ (`ab -n 1000 -c 5 http://localhost:5132/lectures`)
- **Пропускна здатність (Throughput):** `40.55 req/s` (медіана з 3 прогонів: `47.26`, `40.55`, `39.90 req/s`)
- **Середній час відповіді (`Time per request, mean`):** `123.32 мс` (`24.66 мс` у розрахунку на всі паралельні запити)
- **Перцентилі часу відповіді:** $p_{50} = 117\text{ мс}$, $p_{90} = 174\text{ мс}$, **$p_{95} = 192\text{ мс}$**, $p_{99} = 240\text{ мс}$, $\max = 319\text{ мс}$
- **Кількість невдалих запитів:** `0 (0%)`
- **Швидкість передавання даних:** `69 224.22 KB/sec` (~67.6 МБ/с)

## 3. Етап 2. Стрес-тестування та Spike-тестування (Grafana k6)

### 3.1. Сценарій стрес-тестування ([`stress-test.js`](benchmark/stress-test.js))
Використано інструмент **k6** із перевіркою статусу `200 OK`, паузою між ітераціями `sleep(1)` та порогами якості (`thresholds`):
- `http_req_failed: ['rate<0.01']` (частка помилок < 1%);
- `http_req_duration: ['p(95)<500']` (95% запитів швидше ніж 500 мс).

Для точного порівняння показників проведено як **ізольовані 20-секундні прогони** на фіксованих рівнях `10`, `50`, `100`, `200` VU, так і **комплексний ступінчастий прогін** (`10 VU → 50 VU → 100 VU → 200 VU → 0 VU` загальною тривалістю 90 с):
- На рівні **10 VU**: `8.36 req/s`, середній час `158.92 мс`, **$p_{95} = 239.28\text{ мс}$** — поріг `< 500 мс` успішно виконується.
- На рівні **50 VU**: `27.38 req/s`, середній час `747.69 мс`, **$p_{95} = 1026.00\text{ мс}$** — поріг `< 500 мс` порушено більш ніж удвічі.
- На рівні **100 VU**: `38.61 req/s`, середній час `1556.01 мс`, **$p_{95} = 2053.75\text{ мс}$**.
- На рівні **200 VU**: `45.20 req/s`, середній час `3324.68 мс`, **$p_{95} = 3917.13\text{ мс}$**.
- **Комплексний ступінчастий тест (`stages`):** виконано `2 951` запит (передано `5.2 ГБ` даних зі швидкістю `57 МБ/с`), середня пропускна здатність `32.57 req/s`, середній час `1183.32 мс`, медіана `765.10 мс`, **$p_{95} = 3144.66\text{ мс}$**, невдалих запитів `0 (0.00%)`.

### 3.2. Додаткове завдання: Spike Testing ([`spike-test.js`](benchmark/spike-test.js))
Проведено тест різкого стрибка навантаження: `10 VU (10 с) → 300 VU за 5 с → утримання 300 VU (20 с) → спад до 10 VU (5 с) → 0 VU (5 с)`.
- Виконано запитів: `1 436` (передано `2.5 ГБ`).
- Пропускна здатність: **`31.66 req/s`** (нижче, ніж при стабільних 100–200 VU!).
- Час відповіді: середній **`4908.59 мс`**, медіана `5335.70 мс`, $p_{90} = 6518.77\text{ мс}$, **$p_{95} = 6619.86\text{ мс}$**, максимум **`7011.72 мс`**.
- Споживання RAM процесом `study-mentor-api`: стрибок до **`1617.2 МБ (~1.62 ГБ)`**.
- Після зниження навантаження з 300 до 10 VU сервер відновив нормальний час відповіді без відмов з'єднань (`0%` помилок HTTP).

![Grafana k6 Spike Test 300 VU](screenshots/benchmark/k6-spike-300vu.png)

## 5. Аналіз результатів та визначення межі стабільної роботи

1. **Динаміка пропускної здатності (Throughput):**
   - Для `GET /lectures` пропускна здатність у `ab` зростає з `40.55 req/s` ($c = 5$) до `58.49 req/s` ($c = 100$), після чого виходить на плато (~`55–58 req/s`).
   - Для `GET /tests?sourceFlashcardId=…` пропускна здатність зафіксована на рівні **`5.17–5.44 req/s`** незалежно від кількості одночасних запитів ($c = 5, 20, 50$) — система повністю впирається у внутрішню обробку запиту.

2. **Динаміка часу відповіді (Response Time) та межа стабільної роботи:**
   - **Межа стабільної роботи для `GET /lectures`:** при цільовому критерії $p_{95} < 500\text{ мс}$ система стабільно працює до **`15–18` одночасних запитів / активних віртуальних користувачів** (при `10 VU` у `k6` $p_{95} = 239.28\text{ мс}$, при $c = 20$ в `ab` $p_{95} = 540.00\text{ мс}$, при `30 VU` у `k6` $p_{95} = 538.72\text{ мс}$).
   - Починаючи з **`50 VU`**, спостерігається виражена лінійна деградація затримки: $p_{95} = 1026.00\text{ мс}$ при `50 VU`, `2053.75 мс` при `100 VU`, `3917.13 мс` при `200 VU` та **`6619.86 мс`** при піковому стрибку `300 VU`.
   - Для `GET /tests?sourceFlashcardId=…` навіть при $c = 5$ система не вкладається в поріг стабільної роботи ($p_{95} = 1122\text{ мс}$).

3. **Частка помилок (Error Rate) та використання ресурсів:**
   - На всіх перевірених рівнях навантаження (включно зі стрибком до `300 VU`) сервер Kestrel не допустив жодної помилки HTTP 5xx або скидання з'єднання (`Failed requests = 0`, `Error Rate = 0.00%`).
   - Водночас під час росту навантаження спостерігається непропорційне зростання споживання оперативної пам'яті процесом `study-mentor-api`: від `345.8 МБ` ($c = 5$) до `861.6 МБ` ($c = 100$) і **`1617.2 МБ`** під час Spike-тесту (`300 VU`).

4. **Гіпотези щодо причин деградації (для етапів Profiling та Database Optimization):**
   - **Гіпотеза 1 (`GET /lectures`):** виконанням 3 окремих запитів до БД (`Lectures`, `Majors`, `Subjects`) без `AsNoTracking()` в одному scoped `AppDbContext` створюються тисячі об'єктів у `ChangeTracker`, що викликає автоматичний `NavigationFixer` та інтенсивну роботу Garbage Collector (перевіряється у звіті [`profiling-report.md`](profiling-report.md)).
   - **Гіпотеза 2 (`GET /tests?sourceFlashcardId=…`):** у `TestEndpoints.GetAll` фільтрація за `sourceFlashcardId` виконується в пам'яті C# після виклику `service.GetAllAsync(ct)`, який завантажує з PostgreSQL усі 2 000 тестів, 6 000 питань і 24 000 варіантів відповідей (перевіряється у звіті [`db-optimization-report.md`](db-optimization-report.md)).
